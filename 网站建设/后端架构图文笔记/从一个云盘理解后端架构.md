# 从一个简单云盘，理解程序的后端架构设计

> 给有基础编程经验、尚未系统学习后端架构的大学生。
>
> 本文根据 Tiago 的视频 Fundamentals of Backend Architecture — How to Design Scalable Software 整理。正文以原片字幕、官方章节与关键手绘画面为依据；补充知识均标为「延伸理解」。所有架构图都是教学示意，不是 Google Drive 的真实内部架构。

假设你已经写过一个程序：前端发出请求，后端执行逻辑，把结果返回。现在，你想做一个简单云盘，让同学上传课程资料、查看文件列表、下载文件。

最开始，一台服务器就能工作。然后问题来了：重启会不会丢数据？人多了为什么变慢？为什么上传一个大文件，会拖慢其他人的查询？上传成功了，缩略图还没生成，算成功还是失败？

后端架构设计，就是让这些问题有明确的答案。 它安排系统中各部分的职责、通信方式和数据归属，并决定发生故障或负载增加时，系统如何应对。

原片开头强调：架构是为了支持业务，而不是为了收集技术名词。本文也沿着这个思路展开——每增加一个组件，都先解释它要解决什么问题，再讨论它带来的代价。

## 阅读地图：我们的云盘会遇到什么问题？

| 阶段  | 新问题                 | 要理解的组件或概念        |
| --- | ------------------- | ---------------- |
| 1   | 程序重启，内存数据怎么办？       | 有状态服务器           |
| 2   | 数据能不能独立于应用实例？       | 数据库分离、无状态服务器     |
| 3   | 多台服务器怎样共同处理请求？      | 负载均衡             |
| 4   | 算力不足，增加数量还是升级机器？    | 水平、垂直扩展与自动扩缩容    |
| 5   | 多团队、多业务如何分工？入口如何统一？ | 微服务、API 网关、认证与授权 |
| 6   | 大文件上传为什么不该挤占应用服务器？  | 元数据、对象存储、限时上传链接  |
| 7   | 上传后的处理如何避免互相拖累？     | 同步、异步、消息代理       |
| 8   | 重复查询同一个文件的信息怎么办？    | 缓存               |
| 9   | 元数据已经很快，为什么下载仍然慢？   | CDN              |
| 10  | 一个用户的过量请求如何不影响别人？   | 限流               |

## 1. 第一版：一台服务器就能跑起来

对应原片：04:07，有状态服务器。

**当前需求与问题。** 第一版只需支持少量用户，我们把请求处理和文件索引都放在一个程序实例里。原片用 Go 的内存映射举例：根据文件 ID 找到文件位置。所谓「实例」，就是正在运行的一份程序。

![图1：用户请求与业务状态集中在一个应用实例中](01-stateful.png)

*图 1｜依据原片 04:37 画面重画。重点是状态与实例耦合；文件字节的完整存储方式留到第 6 阶段讨论。*

**请求如何流动。** 客户端发出上传或查询请求，服务器在本地处理，读取或修改实例里的索引，然后返回响应。此时所有事情都集中在一个地方，很容易理解。

**为什么采用这种结构。** 它需要的组件少，开发和调试都直接。对刚开始验证功能的项目，这种简单性很有价值。

**收益、代价与适用条件。** 收益是快速实现；代价是业务状态依赖这个实例。原片里的索引存放在内存中，程序结束后它就会消失。复制出第二个实例，也不会自动让两个实例拥有一致的索引。

**容易混淆。** 「服务器崩溃就会丢掉一切」不是普遍成立的规律：原片讨论的是内存状态。 延伸理解：写在可靠磁盘上的数据，不会仅因为进程退出就自动消失；但本地磁盘仍可能让数据与某台机器绑在一起，迁移和多实例共享都需要额外设计。

## 2. 分离数据库：程序可以重启，数据应该继续存在

对应原片：05:21，无状态服务器。

**当前需求与问题。** 我们希望应用实例可以替换、重启，也希望以后多个实例看到同一份业务数据。例如，小张上传的资料，不应只有处理那次请求的实例知道。

![图2：应用负责处理请求，独立数据库负责持久保存状态](02-stateless.png)

*图 2｜依据原片 07:10 画面的数据库分离关系重画，聚焦一个应用实例的完整请求与响应；图 3 再展开多实例。*

**请求如何流动。** 客户端请求应用，应用向关系数据库查询或写入，拿到结果后返回给客户端。关系数据库用表组织数据；「持久化」表示数据不会随着应用进程结束而消失。

**为什么引入数据库。** 它把两个职责拆开：应用处理请求，数据库保存状态。这种做法叫「关注点分离」——让不同组件专注于不同问题。

**收益、代价与适用条件。** 应用实例不再是重要业务状态的唯一保存者，替换实例更容易，也为多实例扩展打下基础。代价是多了一次网络访问，以及数据库的部署、备份和维护工作。需要保存用户、文件列表等长期数据时，这种分离很自然。

**容易混淆。** 「无状态服务器」不代表没有内存、没有变量，也不代表整个系统没有状态。这里指重要业务状态不依赖某个特定应用实例，而由外部存储承接。原片也提醒：数据库故障仍可能影响业务。

**延伸理解：** 外置数据库并没有自动解决所有高可用问题，持久化也不等于备份。系统还需要考虑数据库恢复，以及多个请求同时修改数据时的正确性。

## 3. 多实例与负载均衡：加了机器，还要有人分流

对应原片：08:00，负载均衡；12:48，Nginx 演示。

**当前需求与问题。** 云盘变热门，一台应用实例处理不过来。我们启动第二台，却发现用户仍集中访问第一台。增加资源与用好资源，是两件事。

![图3：负载均衡器将请求分配给共享数据库的应用实例](03-load-balancing.png)

*图 3｜依据原片 11:00 的负载均衡手绘图及前一阶段的共享数据库语境重画。绿色箭头表示实例访问同一数据库；为保持简洁，省略响应路径。*

**请求如何流动。** 用户先到负载均衡器，再被分配给某个应用实例。实例执行逻辑，访问共享数据库，返回结果。

**为什么引入负载均衡器。** 负载均衡器是请求的分配者，帮助多个实例共同承担工作。它可以根据策略选择目标实例，也可以避开不可用的实例。

| 原片提到的策略 | 简短解释 | 初学者应理解的取舍 |
|---|---|---|
| 轮询 Round Robin | 请求依次交给 A、B、C | 简单，但请求数均匀不等于工作量均匀 |
| 加权轮询 | 根据权重给不同实例分配请求 | 可适应不同处理能力，权重需要合理设置 |
| 会话亲和 Sticky Session | 尽量让同一用户回到同一实例 | 有利于使用实例本地临时状态，但会增加用户对特定实例的依赖 |
| 最少连接 Least Connections | 优先选择活跃连接较少的实例 | 连接数提供一种负载线索，仍不等于真实计算成本 |

原片的具体例子是：一个用户上传文件，另一个用户获取文件。它们都算一次请求，但资源开销不同，轮询不会自动知道每个请求有多重。

**收益、代价与适用条件。** 收益是分散负载、统一入口；代价是新增组件和配置，也需要考虑其自身故障。出现多个可替代的应用实例时，它才有实际分流价值。

**容易混淆。** 健康检查回答「实例是否还能服务」，负载测量回答「实例有多忙」。原片将二者连续讲解，理解时应区分。还有，增加应用实例不代表数据库、带宽等下游资源也自动变强。

**原片实践。** 作者用 Docker Compose 运行三个相同的 Go HTTP 服务，Nginx 的 `upstream` 定义服务器组。访问 `/rr` 并刷新，编号在不同服务间切换；访问 `/sticky`，会话 Cookie 帮助请求回到同一个服务。本笔记没有把未逐行核实的配置补写成所谓「视频原代码」。

**延伸理解：** Nginx 的反向代理转发通常不要求浏览器重新导航到另一台服务器。原片口语中的“redirect”在这里可理解为分流或转发，不应一概理解成 HTTP 302 重定向。[Nginx 官方负载均衡说明](https://nginx.org/en/docs/http/load_balancing.html)

## 4. 水平与垂直扩展：更多台，还是更强一台？

对应原片：14:55，不同的扩展方式。

**当前需求与问题。** 请求继续增加，需要更多处理能力。我们可以增加实例，也可以升级单机。架构设计要考虑哪条路能缓解眼前的瓶颈。

![图4：水平扩展增加实例，垂直扩展增强单机资源](04-scaling.png)

*图 4｜依据原片 14:55—17:37 的概念讲解新绘制的比较图，不是某一帧的机械复制；它不描述请求先后顺序。*

**请求如何流动。** 水平扩展后，请求由负载均衡器分给更多实例，沿用图 3 的链路。垂直扩展后，链路通常不变，同一个实例获得更多 CPU、内存或存储资源。

**为什么需要这两种办法。** 水平扩展提供更多并行处理者，垂直扩展增强一个处理者。可以把它们理解为「增加服务窗口」和「增强单个窗口的处理能力」，但实际效果仍取决于程序瓶颈。

**收益、代价与适用条件。** 两者都能增加资源，也都需要付费。原片强调可以组合使用。自动扩缩容按负载增减实例，减少长期维持大量空闲资源的成本。

**容易混淆。** 负载均衡负责选择请求落点，自动扩缩容机制负责增减资源。云产品可以把它们集成起来，但它们仍是不同职责。

**延伸理解：** 更多 CPU 未必能解决磁盘或数据库瓶颈；水平扩展也不是线性、无限增长。自动扩容有启动时间和资源上限，垂直扩容有单机规格上限。原片提到 Serverless，可理解为平台承担更多服务器管理工作，而不是系统中不存在服务器。

## 5. 微服务与 API 网关：分工以后，系统怎么合作？

对应原片：17:37，微服务；约 21:16，引入网关；23:30，认证。

**当前需求与问题。** 业务开始盈利，团队也变大。文件、通知、实时同步各有自己的需求和负载。把所有功能集中在一个应用里，可能让不同团队和工作负载互相牵制。

「微服务」指把系统拆成职责明确、可以分别运行的服务。原片按云盘业务讨论文件、认证、通知、实时同步等领域，并强调这是一条复杂的道路。

![图5：网关统一入口，内部服务分别承担认证和业务职责](05-gateway.png)

*图 5｜依据原片 23:05 的网关与私有网络画面，以及 23:30—27:14 的认证、授权讲解重画。为突出权限边界，只展开文件与认证服务；通知等服务在后续图中出现。此图省略网关前的负载均衡。*

**请求如何流动。** 客户端把请求交给 API 网关。网关按业务路由：登录请求到认证服务，文件请求到文件服务。需要时，它可以调用多个服务，将结果聚合后返回。

API 是程序之间约定的交互接口。API 网关是统一的业务入口，负责路由，也可能承担认证、限流和响应聚合。原片把内部服务放进私有网络，让外部用户不能直接访问它们的内部端口；业务 API 经网关进入。

**为什么引入这些组件。** 服务拆分解决职责和团队分工；网关解决客户端面对多个服务时的入口协调问题。它们回答的是不同问题。

### 登录之后，为什么还要检查文件权限？

认证 Authentication 回答「你是谁」；授权 Authorization 回答「你能做什么」。小张已成功登录，并不意味着他能下载小李的私有文件。

原片的登录流程是：客户端提交有效凭据，认证服务核验并签发 Token。Token 是后续请求携带的令牌；原片以 JWT 为例。网关可以检查其签名与有效期，无效认证在示例中返回 HTTP `401`。采用可本地验证的令牌时，不一定每次请求都要往返认证服务。

文件服务仍应判断当前身份有没有执行该文件操作的权限。原片明确说明，授权可以在各业务服务中进行。

**收益、代价与适用条件。** 各领域能分别演进、扩展，不同团队可以负责不同服务；代价是部署与通信变复杂，还要处理跨服务调用的失败。网关自身也可能成为瓶颈，因此原片提醒它同样可以扩展。

**容易混淆。** 负载均衡主要选择哪个实例，网关主要理解请求该去哪个业务服务；产品能力可能重叠。网关也不是天然的万能协调者。私有网络限制可达性，并不能代替业务授权。

**延伸理解：** 签名有效只说明令牌通过相应验证，并不能自动完成所有业务判断。实际 JWT 验证还需匹配算法、签发者、受众等规则；不能把解码 JWT 当成验证它。常见签名 JWT 的载荷可被读取，也不等于内容已加密。[JWT 标准 RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)

**延伸理解：** 小团队的课程项目通常可以先做结构清晰的模块化单体——仍在一个应用中，但把文件、用户、通知等代码职责分好。只有独立部署、团队边界或负载隔离确有收益时，再考虑拆服务。微服务不是「更高级项目」的必选标签。

## 6. 对象存储：元数据与文件字节走不同路线

对应原片：27:14，文件服务与上传。

**当前需求与问题。** 同学上传 200 MB 视频。若这些字节全部经过应用服务器，会占用带宽和连接，还可能超时。查询一个文件的名称却只需要很少的数据，不应被大文件中转拖住。

「元数据」是描述文件的信息，如文件 ID、名称、大小、类型和存储位置；「文件内容」是视频、图片或 PDF 的实际字节。对象存储专门保存这类文件对象，原片举例为 S3、云存储桶。

![图6：先申请上传并保存元数据，再向对象存储直传文件内容](06-object-upload.png)

*图 6｜依据原片 31:00 的元数据表、上传 URL 和对象存储图重画。蓝色链路处理小的业务请求，绿色链路传输文件字节。返回上传链接的箭头折叠了经过网关的响应路径；链接生成的存储 SDK 调用细节未展开。*

**请求与数据如何流动。** 1. 客户端向 API 申请上传，提供名称、大小等元数据。
2. 网关验证身份并路由，文件服务检查操作权限。
3. 文件服务在数据库创建元数据记录。
4. 后端返回限时上传链接。
5. 客户端使用链接，直接向对象存储上传文件字节。

**为什么引入对象存储。** 应用处理业务规则，数据库维护可查询的元数据，对象存储承接文件内容。大文件不再必须由应用中转，降低应用服务器的带宽和连接压力。

**收益、代价与适用条件。** 处理大文件或大量文件时，这种分工很有价值；代价是引入新的存储服务，上传不再只有一个请求，前端要处理两步流程，后端也要协调文件与元数据。

**容易混淆。** 直传绕过的是应用服务器的数据中转，不是权限控制。原片提到上传链接有短有效期、可限制上传大小，但“只要短时间就可以不认证”的口语表述不能直接当成安全实现规则。

**延伸理解：** 以 S3 预签名 URL 为例，链接授权的是特定对象、操作和时限，客户端无需持有云平台长期凭据。持有该链接的人可以在限制范围内使用它，链接本身就应受到保护。具体大小约束取决于上传方式与策略；不是任意 URL 自动拥有文件大小限制。[S3 官方预签名 URL 文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

**延伸理解：** 数据库记录创建成功，不代表文件已经上传成功。可以用「待上传、已上传、处理完成」等状态表达阶段，并设计超时清理或确认机制。这些生产细节未在原片完整展开。

## 7. 消息代理：上传成功以后，让后续任务各自完成

对应原片：32:30，事件代理。

**当前需求与问题。** 视频上传后，还要生成缩略图、同步到其他设备、发送提醒。假如上传流程直接依次调用三个服务，其中一个很慢或宕机，整个流程就会被牵连。发布方还得知道全部下游。

「同步通信」通常让调用者等待结果；「异步通信」让处理可以在稍后完成。「事件」描述已经发生的事情，例如「文件已上传」。消息代理 Broker 在发布方与接收方之间保存、分发消息。

![图7：对象存储发布上传事件，多个服务通过消息代理独立消费](07-event-broker.png)

*图 7｜依据原片 36:30 的对象存储 → Broker → 下游服务画面，以及 32:30—37:32 的讲解重画。虚线表示异步事件，不是文件字节；确认与重试列在代理职责中，未逐条画出协议返回箭头。*

**事件如何流动。** 对象存储的上传完成事件进入消息代理。缩略图、实时同步、通知服务分别订阅相关事件并处理。将一个事件送给多个订阅方叫「扇出」Fan-out。

原片介绍了消息持久化、确认、失败重试，以及死信队列 DLQ：多次仍无法处理的消息进入单独区域，配合告警供开发者排查。死信队列是失败处理的入口，不是问题自动解决的终点。

**为什么引入代理。** 上传完成与后续加工不必同步绑在一起，发布方也不用逐个维护所有下游的地址与调用逻辑。

**收益、代价与适用条件。** 收益是解耦、缓冲和更明确的失败处理；代价是消息基础设施和运维复杂度，用户可能先看到文件，再看到稍后生成的缩略图。能接受这种分阶段完成体验的任务适合异步处理。

**容易混淆。** 消息可靠性来自持久化、确认、重试等设计与配置，不是用了 Kafka 或 RabbitMQ 就自动保证。通知消息不等于把完整视频放进队列。同步调用也不总是错的：需要立即返回权限判断结果的请求，通常就不能简单替换为“稍后处理”。

**延伸理解：** 重试可能使同一事件被处理多次。消费者应考虑「幂等」——重复处理不产生重复副作用，例如不要因为重投一次消息，就向同学连续发送两份通知。消息代理也不能自动解决数据库与对象存储之间的所有一致性问题。

## 8. 缓存：不必每次都重新查询同一份元数据

对应原片：37:32，缓存与 CDN。

**当前需求与问题。** 一份热门课程资料被反复打开。每次查询文件名称、大小和位置，都访问数据库，做了很多重复工作。缓存是保存近期或高频数据副本的组件，用来减少重复获取或计算。

![图8：文件服务先查 Redis，未命中时查询数据库并回填缓存](08-metadata-cache.png)

*图 8｜依据原片 41:50 的 Files、Cache、Relational DB 节点及 41:33—43:16 的算法讲解重画。图明确保留文件服务作为数据库查询者和缓存回填者，避免误画成 Redis 自己去查询数据库。*

**数据如何流动。** 服务先用文件 ID 查询缓存，命中就返回元数据；未命中则查询数据库，服务拿到结果后写入缓存，再向调用方返回。原片使用 Redis——一种支持内存键值访问的数据存储。

**为什么引入缓存。** 反复读取的小数据可以更快获取，同时减少数据库承担的重复查询。原片特别区分文件元数据与文件字节：把大视频直接塞进 Redis，通常不是这里的合理选择。

**收益、代价与适用条件。** 高频、可重复利用的元数据读取能受益；代价是内存、额外组件，以及副本与数据库可能不一致。很少被读取的数据或不停变化的数据，不一定值得缓存。

**容易混淆。** 缓存命中文件名和位置，不代表已经获取了完整视频。缓存也是一种存储，但在本案例中，它不承担数据库的权威数据角色。原片关于某些平台可能把热门视频放入 RAM 的旁例带有推测语气，本文不把它作为已核实的企业内部实现事实。

**延伸理解：** 这个读取方式通常称为 Cache-aside，旁路缓存。文件改名或权限变化后，要考虑失效、更新和过期策略。只设置过期时间并不能自动解决权限泄露；用户能否读取某文件，仍须按有效权限判断。原片没有完整讲解缓存失效、穿透或击穿方案。

## 9. CDN：元数据很快，文件下载还需要离用户更近

对应原片：41:11 引入 CDN，43:18 开始集中展开。

**当前需求与问题。** 元数据查询只花很少时间，但大视频从远处传到用户设备仍然慢。CDN，内容分发网络，在不同地区部署边缘节点，在靠近用户的位置缓存和分发内容。

![图9：客户端从附近 CDN 获取内容，未命中时 CDN 回源对象存储](09-cdn.png)

*图 9｜依据原片 43:40 的 CDN 位于集群外侧的画面，以及 43:18—44:45 的首次请求、边缘缓存讲解重画。原画面未逐条展开 CDN 请求箭头，这里按讲解拆成四步；只展示文件分发链路，省略业务元数据请求。*

**文件如何流动。** 客户端请求附近的 CDN 节点。命中时直接返回缓存内容；未命中时回源获取文件，保存副本，再返回给用户。图中源文件由对象存储提供，沿用上一阶段对文件内容的归属。

**为什么引入 CDN。** 减少网络距离与源站重复传输的压力。原片以里斯本附近用户读取同一文件为例说明效果；其中延迟数字是示意，不是本文给出的性能保证。

**收益、代价与适用条件。** 重复访问、地域分散的文件分发可以受益；代价是流量费用、缓存管理和访问控制。对于很少重复访问的私有文件，命中率和收益需实际评估。

**容易混淆。** Redis 在这里缓存小的元数据，CDN 缓存文件内容，对象存储保存源文件。三者不能简单互换。命中率也不是永远 100%，第一位用户仍可能承担回源等待。

**延伸理解：** 私有云盘必须设计 CDN 的访问控制、缓存键和失效机制，例如使用受限签名链接；不能为了下载更快就把文件公开。文件内容可以绕过应用服务器分发，但业务授权仍须在相应链路中得到执行。

## 10. 限流：能扩容，也不能无限接收请求

对应原片：44:45，限流。

**当前需求与问题。** 某个用户不停刷新或恶意调用接口，让系统资源被占满。即使自动扩容能维持响应，也可能造成账单上涨。限流 Rate Limiting 是对某个标识在一定范围内可使用的请求或资源设定限制。

![图10：入口识别请求，查询共享计数，超限返回 429](10-rate-limit.png)

*图 10｜依据原片 44:45—46:32 关于入口限流、缓存计数和 HTTP 429 的讲解绘制的流程图；不是对未完整展示的限流算法代码的复现。*

**请求如何流动。** 入口识别用户 ID、IP 等标识，在缓存中记录或查询一段时间内的请求次数。未超限则继续路由业务；超限则返回 HTTP `429`，表示请求过多。

**为什么引入限流。** 它限制一个使用者能占据的资源，保护其他用户体验，也控制系统成本。原片的每分钟 10 次只是讲解例子，不是云盘应使用的固定参数。

**收益、代价与适用条件。** 收益是保护容量和公平性；代价是正常用户也可能被误伤，还要定义标识、窗口、阈值和计数方式。登录、上传等昂贵接口与简单查询接口，未必适合相同的限制。

**容易混淆。** 限流减少允许进入的工作量，扩容增加可处理的工作量，两者可以配合。限流不能代替认证，也不能代替文件权限判断。

**延伸理解：** 大学宿舍可能多人共享一个公网 IP，只按 IP 限制可能误伤。多个入口实例还要协调计数，并考虑更新的原子性。窗口计数、滑动窗口、令牌桶有不同取舍；本片没有逐一展开，不能把图 10 当作完整生产实现。

## 学完以后，怎样评估自己的课程项目？

不要先问「我是不是也要上十个组件」，先问「我的程序已经遇到了哪个问题」。

| 如果出现这个现象 | 先检查什么 | 可能的方向 |
|---|---|---|
| 重启后业务数据丢失 | 状态是否只在实例内存中 | 持久化与数据分离 |
| 请求慢，但不知道慢在哪里 | 耗时发生在计算、存储还是网络 | 先定位瓶颈，再扩展 |
| 上传影响普通查询 | 文件是否经过应用中转 | 对象存储直传 |
| 后续任务失败拖累主流程 | 必须同步完成的边界是什么 | 事件与异步处理 |
| 数据库重复读取相同内容 | 读取热点、更新频率 | 元数据缓存 |
| 远距离下载热门文件慢 | 文件分发距离、访问重复程度 | CDN |
| 单个用户占据过多资源 | 身份标识、资源成本 | 限流 |

**延伸理解：** 表中的瓶颈检查与课程项目建议是对原片思路的教学应用。具体选型应依赖观测数据、团队能力和预算。对缓存、队列、微服务的收益评估，不能只看它们“听起来更强”。

## 术语速查表

| 术语 | 一句话理解 | 别与什么混淆 |
|---|---|---|
| 实例 Instance | 正在运行的一份程序 | 一台机器可能运行多个实例 |
| 有状态 Stateful | 处理依赖某个实例持有的状态 | 不表示所有状态都不可靠 |
| 无状态 Stateless | 关键业务状态不依赖特定应用实例 | 不表示系统无数据 |
| 持久化 Persistence | 数据能跨越应用进程的生命周期 | 不等于备份或高可用 |
| 水平扩展 | 增加实例数量 | 不是升级同一台机器 |
| 垂直扩展 | 增加单机资源 | 不保证解决所有瓶颈 |
| 负载均衡 | 在实例间分配请求 | 不等于自动扩容 |
| 会话亲和 | 尽量把同一用户送到同一实例 | 不保证该实例永远可用 |
| 微服务 | 按职责拆成可分别运行的服务 | 不是所有项目的默认答案 |
| API 网关 | 对外统一业务入口与路由层 | 不自动消除单点故障 |
| 认证 Authentication | 验证身份 | 不表示拥有全部文件权限 |
| 授权 Authorization | 判断某身份可执行什么操作 | 不只是登录成功 |
| JWT | 可携带声明的令牌格式 | 解码不等于验证，签名不等于加密 |
| 元数据 Metadata | 文件名称、大小、位置等描述 | 不等于文件字节 |
| 对象存储 | 保存文件对象内容的存储服务 | 本案例中不取代元数据数据库 |
| 同步通信 | 调用方等待结果 | 并不天然不可靠 |
| 异步通信 | 允许接收方稍后处理 | 不等于无需结果与失败管理 |
| 消息代理 Broker | 在发布者与消费者之间传递消息 | 不等于文件存储服务 |
| 扇出 Fan-out | 同一事件分发给多个订阅者 | 不等于每个消费者竞争同一份任务 |
| 死信队列 DLQ | 收容无法正常处理的消息 | 不表示错误已修复 |
| 缓存 Cache | 保存可重复利用的副本 | 不自动保持与源数据一致 |
| CDN | 靠近用户分发内容的网络 | 不自动让私有文件公开 |
| 限流 | 限制请求或资源使用量 | 不代替认证、授权 |
| 幂等【延伸理解】 | 重复执行不产生额外业务副作用 | 不是不允许请求重试 |
