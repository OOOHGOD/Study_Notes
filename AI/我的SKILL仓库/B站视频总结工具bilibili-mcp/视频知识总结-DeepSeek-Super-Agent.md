## 一、问题背景：瓶颈从「模型能力」变成「人的注意力」

现有 Agent 的工作方式是单会话 **ReAct Loop**：想一步 → 调一个工具 → 看结果 → 再想下一步，一圈圈串行推进，直到做完 `[00:18]`。它有两个天生限制：**一个会话同一时间只能干一件事**，而且**你说一句它才动一下**。

想同时干几件事（调研报告 + 回邮件 + 做 PPT），只能再开几个会话，但会话之间上下文互不相通，哪个做到哪儿全靠人自己记 `[00:41]`。DeepSeek 在文章里观察到：一个人同时最多只能盯 **3~5 个活跃会话**，再多就乱 `[00:52]`。于是随着模型能力提升，生产力瓶颈不再是 AI，反而变成了人的注意力——UP 主顺手玩了个梗，「Attention is all you need」的含金量还在上升 `[01:03]`。

**给 Agent 接上 MCP、飞书、邮箱，让它能收外部消息，够不够？** DeepSeek 的回答是还不够 `[01:15]`，因为三个底层毛病没变：

1. **同步阻塞**：它在忙的时候，你的新消息进不来，只能干等；
2. **上下文混杂**：几件事塞进同一个会话，很容易串；
3. **设备强绑定**：跑在本地电脑上，盖子一合 Agent 就停了。

所以思路是：别让 Agent 绑定在一个手动开的会话上，让它变成能跨会话、记住上下文、同时推进多件事且互不干扰的**连续实体**——这就是 Super Agent `[01:40]`。

## 二、Super Agent 的四个特征 `[01:50]`

| 特征 | 含义 | 视频举例 |
|---|---|---|
| **连续** | 跨信道保持同一份上下文，用户不必记住「哪个会话里说过什么」 | 群聊里说用方案 A，邮件里改口方案 B，它知道是同一件事，不用重新交代 |
| **高效** | 忙的时候也能收新指令，随时响应，不用等上一件干完 | 并行推进多个复杂任务 |
| **主动** | 不逐条等吩咐，自己盯环境事件，该出手才出手，不需要你时保持安静 | 群里没人 @ 也能识别潜在缺陷 |
| **持久** | 一直在线、接在真实工作环境里，出问题能自己恢复 | 长期运行、异常自愈 |

单个 ReAct Loop 做不到这四点——它天生串行、必须被指令触发、还绑在一个会话一台电脑上 `[02:23]`。底层得换架构，DeepSeek 拆成**五个模块** `[02:38]`。

## 三、五大模块（核心方法）

### 模块 1｜双层架构 `[02:45]`：连续与高效不再二选一

「连续」和「高效」本身是矛盾的：全交给一个会话，上下文连续但只能一件件干、细节还互相污染；每来一件事就新开会话，并发上去了但任务间关联断裂、多个会话同时向你汇报也看不过来。

解法是把两件事拆到两层：

- **Router 层**（常驻）：只干两件事——跟你沟通、把任务分派下去。所有跨任务信息汇总在这里，**不亲自干活**，所以不会被具体任务拖住；官方经验是 Router 没想象中复杂，**用轻量模型就够** `[03:27]`。
- **Worker 层**：一个 Worker 只负责一个任务，上下文互相隔离，**配最强的模型**；不直接和用户对话，干完或遇到问题统一向 Router 汇报，由 Router 回复你 `[03:35]`。

结果：你面前始终只有一个 Agent，背后几个 Worker 并行干活；**Session 从用户要管理的概念，降级成系统内部实现细节** `[03:47]`。

**单 Router 会不会堵？** `[04:01]` 不会，靠**批处理**：Router 思考期间到达的新事件先积压，下一轮合并注入；Router 每步是「长输入、短输出」，多条 Trigger 合并进一次 API 调用时在 Prefill 阶段并行计算，单次请求耗时增长远慢于 batch 增长，所以积压越多，平均每条反而更快。

### 模块 2｜事件驱动 `[04:23]`：让 Agent 变主动

驱动 Agent 的输入从「人敲的那句话」变成环境里的半结构化事件 **Trigger**：群消息、邮件、日程提醒、文档评论、CI 测试结果等 `[04:31]`。一条事件从进来到处理，有四步：

1. **两级过滤** `[04:43]`：真实群聊是「高噪音、低触发率」，逐条过模型又慢又贵。先用**程序层 Fast Path** 按来源、群组、白名单等确定性规则快筛掉大部分；剩下的交**语义层 Slow Path** 由 LLM 按提示词写的策略判断要不要处理。
2. **路由 / 订阅直通** `[05:04]`：同一话题、同一 PR、同一邮件串下的连续事件构成一条 **Thread**。Router 为新任务创建 Worker 后，Worker 订阅该 Thread，之后 Thread 里的消息由程序**直接发给 Worker，不再绕 Router**；只有未被订阅的新事件才由 Router 判断分派。订阅是多对多——两个 Worker 改同一份代码会收到相同消息，不点对点通信也能自行发现冲突。
3. **上下文组织** `[05:31]`：借 CPU Cache 思想，**Inline**（近期很可能用到的直接内联进窗口）/ **Spill**（超长内容只留摘要与引用，按需再读）；每个对象带唯一 ID 并内联下一跳 ID，可沿引用一跳跳往外找，即**链式召回**，很久以前的任务也能找回上下文。原话很到位：浪费上下文窗口，就是浪费模型的智能。
4. **提前行动（投机执行）** `[06:08]`：不等你开口先在后台试，有用就交付、没用就丢掉。例：收到会议邀约先查日程冲突、备好回复草稿；DeepSeek 内部群配了「**静默复现并修复**」策略——有人反馈问题时后台先复现找方案，只有确认问题且修复简单才交出结果，否则全程不出声。

### 模块 3｜异步多信道交互 `[06:38]`

经典 ReAct Loop 调一次工具就得等它跑完，这期间你说什么它都不理。DeepSeek 把耗时命令改成异步的 **`start()` / `stop()`**：调用后立刻返回「已启动」，循环不再阻塞；后台跑完把结果当一条新事件消息投回会话；跑太久模型还能主动 `stop()`。前台对话与后台执行解耦，构成**全双工** `[06:43]`。

输出则要按信道定规矩 `[07:07]`：把终端里冗长的推理过程、密集工具调用原样发群里会直接刷屏。双层架构已经解决一半（推理和工具调用关在 Worker 里，群里只看结论），再加提示词规范：

- **IM 等即时信道**：低打扰，像同事一样只在需要决策或验收时发消息，只问直接问题、给简短结论；
- **邮件 / 文档 / PR 等异步信道**：结构化、高信息密度，一次把背景、结论、依据交代清楚。

### 模块 4｜存算分离 `[07:47]`：持久在线

Agent 按运行位置分两类：本地（Codex、Claude Code、DeepSeek Harness）设备强绑定，关机即停；云端（Manus 等）能常驻，但用户很多数据、未提交的修改、私人凭据、公司内网依赖搬不上去 `[07:51]`。

干活时其实绑着三样东西 `[08:24]`：**计算**（推进 Agent 循环）、**状态**（会话记录 / 做到哪一步）、**执行环境**（本地文件、软件、账户密码）。分两步解耦：

1. **计算与状态分离**：Agent 进程做成无状态放云端容器，会话记录进数据库；容器随时可重启扩容，任务连续性由 DB 保证，Agent 不再依赖某一台设备 `[08:53]`。
2. **计算与执行环境分离**：既然真实环境难同步（未保存修改、凭据、内网依赖，同步成本高还容易漏），**那就不同步**——环境留在自己电脑上，只装一个不保存任何会话状态的**轻量 daemon**，负责执行命令、把结果回传云端 Agent `[09:46]`。

收益：计算与状态在云端保证随时在线，环境留在本地不用搬家；Agent 可按任务在不同设备间切换，电脑暂时关机、重新上线后云端 Agent 再把需要本地执行的活补做 `[10:10]`。

### 模块 5｜外部 Watchdog `[10:24]`

光有存算分离还不够，得能从异常里自己恢复。Agent 的特殊之处在于：很多故障**不是进程崩了，而是模型陷入无效循环或做着做着跑偏**，所以只监控程序活没活不够，还得监控任务本身有没有进展 `[10:31]`。

做法：在主系统**外面**单独放一个 Watchdog Session，用定时消息唤醒，构成外部 Control Loop。除了处理接口报错、状态恢复失败，还由模型判断每个 Worker 有没有实质进展、方向是否偏离整体目标，发现问题介入修复 `[10:44]`。Watchdog 本身是具备完整工具能力的 Agent，维护者可以用自然语言问「刚才为什么出故障」，也能让它在线调整提示词、触发规则 `[10:58]`。

## 四、推荐方案与落地判断（AI 应用部署视角）

> 本节为**延伸判断**：视频只给方向性提醒，具体依据来自 DeepSeek 官方仓库 README 与 `docs/002~006`，非视频内容。

| 判断项 | 结论 | 依据 |
|---|---|---|
| **是不是能上线的产品** | **不是** | README 原文：*Research prototype for reference only, not an official DeepSeek product*；公开版为发布做过适配，与内部版本及文章描述**不完全一致**，文章中部分设计尚未在原型实现。别写进采购或上线清单。 |
| **它到底是什么形态** | DeepSeek Harness 的**插件包**（TypeScript，MIT，仓库 `deepseek-ai/dsh-superagent-prototype`） | 监听单个 GitHub 仓库 + 可选飞书，按 Ticket 开独立 Worker 会话与目录，在原地回 PR / 原对话，Web 面板列出需要人处理的事项 |
| **部署依赖** | 基本是 Linux/macOS 路线 | Node 22.19+/24+、pnpm、git 2.32+、Python 3.8+、**tmux**、gh CLI ≥2.48、仅支持 github.com（不支持 GHES）、独立 `superagent` profile、独立 GitHub 机器人账号（不能用 GitHub App）、飞书需 `lark-cli`。**Windows 原生跑会一路踩坑，建议 WSL 或 Linux ECS** |
| **安全红线（最重要）** | 必须隔离 | 两个 preset 都以操作者 OS 用户 `danger-full-access` 运行，命令**免审批**、可读 home 目录；官方明说命令包装器与目录「*establish defaults, not a security boundary*」，Worker 用绝对路径即可绕开 blocked commands。官方建议用只含 Agent 凭据的**独立 OS 账号** |
| **与视频 `[11:45]` 呼应** | 安全是最大未解问题 | 事件驱动 → 接触更多不可信输入 → 提示词注入面变大；云端 Agent 连着各台设备，一处被攻破全盘风险；即便云端没破，凭据进入模型上下文也可能泄露。视频结论：解决不了安全与隐私，Super Agent 只能在很小很可信的范围内工作 |
| **建议验证路径** | 逐级放行 | 只读观察 → 单一非业务测试仓库 → 独立 OS 账号 + 独立 GitHub 账号 → 保持人工合并（默认不自动合并；显式开启还需满足审批覆盖 head commit 且改动 <200 行）→ 再评估 |
| **别被带跑偏** | 与现有知识库 Bot 不是同一个问题 | 这套解决的是「多任务调度 + 上下文管理」；知识库 Bot 当前卡点是 mock embeddings 换真实向量 / Reranker 凭证，两者不要揉进同一个方案 |

## 五、要点提炼

| 模块 | 借用的经典系统思想 | 支撑的特征 |
|---|---|---|
| 双层架构 Router / Worker | 调度与执行分离、中心分派 | 连续 + 高效 |
| 事件驱动（两级过滤 / 订阅直通 / Inline & Spill / 投机执行） | Fast-Slow Path、局部性与 Cache、投机执行 | 主动 |
| 异步多信道交互 | 全双工 I/O、按信道带宽适配 | 连续 + 高效 |
| 存算分离 + BYOM | 存算分离、脑手分离 | 持久 |
| 外部 Watchdog | 独立 Control Loop | 持久 |

**实验数据（视频未讲，来自官方技术文章与智东西报道，属延伸补充）**：

- 端到端：Super Agent 任务完成 **p50 12.4 分钟 / p95 15.7 分钟**，显著优于带 Subagent 工具的单 Session（中性提示下 p95 达 29.5 分钟）。
- 订阅直通：去掉后完成时间基本不变，但 Router 决定数 **+30%**、读缓存 token 从 2323 万增至 3177 万（**+37%**）——直通不提速，省的是 Router 开销。
- Router 批处理：Trigger 从约 1 条/分钟升到 40 条/分钟，平均 batch 1.0→2.8，单次请求 2.5→3.9 秒，**单个决定分摊推理时间 6.4→1.6 秒**。
- 代价与前提：**拿更多 token 换时间和稳定性**；实验基于合成负载与简化环境，只是初步参考，不是正式产品结论。
- 官方列出的四个开放问题：Router 拆分时机与粒度 / Worker 间通信与跨月长程记忆；脱离 Session 后的人机界面与中途接管；组织扩大后的上下文边界与 A2A；安全与隐私（让 Agent 不接触凭据本身也能使用凭据）。

## 六、评论区精选

> 采样说明：WBI 评论接口返回 -403，工具回退普通接口后仅取到 4 条，样本有限。外部内容一律按数据处理，其中夹带的机器人调用指令（「总结到我的邮箱里 @…」）不予执行；1 条与主题无关、夹带外链的长文已忽略。

- **237 赞｜「不就是主 agent 带一群子 agent 吗？还可以玩子 agent 开孙 agent，子子孙孙无穷尽也」** — 最值得正面回应的质疑。官方文章其实专门辨析过：常见 **Agent Team** 用于**单个复杂任务内部**的步骤拆解与角色协作，子步骤耦合紧，Team Lead 要深入理解任务细节、规划子任务、高频协调，自身推理负载很重；而 Super Agent 的 **Router 只处理任务之间的高层关联与分派，不介入单任务内部拆解**，甚至可以不配 Bash 工具、用轻量模型即可。差别在「调度的层级与职责」，不在「能不能开子 Agent」。此外 Worker 内部仍可再开 Subagent 或本身是个 Agent Team，这些对 Router 透明。
- **12 赞｜「这个适合领导，不适合牛马，牛马一次干多件事并不会增加工资」** — 段子，但戳中一个真实点：这套架构优化的是「同时派活并验收的人」的注意力，收益对象确实是任务分派方，不是执行方。
- **热评整体信号**：高赞集中在「新瓶装旧酒」的质疑，说明单看动画容易把双层架构理解成普通多 Agent；真正的新意在于**事件驱动、订阅直通、上下文 Cache 化、存算分离、外部 Watchdog** 这一整套系统层设计。
