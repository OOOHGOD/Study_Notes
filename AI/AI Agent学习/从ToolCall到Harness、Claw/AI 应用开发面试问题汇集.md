## 二、项目深挖：MinerU 与多模态 RAG

### 2. 使用 MinerU 解析工业文档时，如何处理图文混排

**先理解**

图文混排的难点不是“把字识别出来”这么简单，还要知道哪一段文字属于哪张图片、页面的阅读顺序是什么，以及表格、公式和正文之间是什么关系。

一种常见方案是：

1. 用 MinerU 做版面分析，识别标题、正文、图片、表格、公式等区域。
2. 对文字区域做文本提取或 OCR，对图片进行裁剪并保存图片路径。
3. 保留页码、坐标、章节标题、图片说明等元数据，防止图文关系丢失。
4. 将正文和图片说明分别生成可检索内容；命中图片时，同时返回原图、图片说明和相邻正文。
5. 对最终输出做抽样检查，重点检查跨页表格、双栏排版、图注错位和 OCR 错字。

**面试可以这样说**

> 我了解的处理方式是先利用 MinerU 做版面分析，把标题、正文、表格、公式和图片区域拆出来，同时保留页码、坐标和章节信息。文字进入文本切片流程，图片则保留原图路径，并通过图注、OCR 或视觉模型生成语义描述。检索命中图片时，不只返回描述，还会把原图和相邻正文一起交给多模态模型。这样可以尽量避免只提取文字以后，图片和上下文关系丢失的问题。

### 3. 为什么选择 MinerU 做文档解析

**先理解**

普通 PDF 读取工具更像“把 PDF 里的字符拿出来”，但工业文档通常包含复杂排版、表格、公式、扫描页和图片。MinerU 的价值在于它更关注文档结构，可以输出适合后续 RAG 使用的 Markdown 或 JSON。

**面试可以这样说**

> 选择 MinerU 主要是因为目标文档版面比较复杂，不只是纯文本。它能够处理 PDF、图片和常见 Office 文档，并把复杂内容转换成结构化的 Markdown 或 JSON，比较适合接入 RAG。相比只用 PyMuPDF 或单独做 OCR，它对版面、表格、公式和阅读顺序的处理更完整。另外它支持本地部署，对内部工业文档的数据安全也更友好。不过我仍然会用抽样数据评估解析准确率，而不是因为工具热门就直接采用。

### 4. 多模态检索中，文本和图片如何映射到同一个向量空间

**先理解**

可以把向量空间理解成一张“语义地图”。意思相近的文本和图片，在地图上的位置也应该相近。

常见做法有两种：

- **共享向量空间：** 使用 CLIP 一类的图文双编码模型。文本经过文本编码器，图片经过图像编码器，两边输出相同维度的向量。训练时让匹配的图文靠近，不匹配的图文远离。
- **统一转成文本：** 先用视觉模型给图片生成描述，再用普通文本 Embedding 对问题、正文和图片描述统一编码。工程上更容易实现，但图片细节可能在描述过程中丢失。

不能随便用两个互不相关的模型分别生成图像向量和文本向量，然后直接计算相似度，因为两个模型的坐标系没有对齐。

**面试可以这样说**

> 如果要真正做到跨模态检索，我会使用 CLIP 这类经过图文对比学习的双编码模型。文本和图片分别经过自己的编码器，但最终进入同一个向量空间，再通过余弦相似度比较。它在训练时已经学习了哪些图片和哪些文字应该靠近。另一种更简单的工程方案，是先把图片转成文字描述，再统一使用文本 Embedding，但这种方式可能损失图像中的细节。

### 5. 为什么引入 Ragas 评测，具体使用哪些指标

**先理解**

只看几个演示结果，很容易产生“感觉回答不错”的错觉。Ragas 的作用是把 RAG 的效果变成可以重复比较的分数，从而判断修改切片、Embedding、召回数量或提示词以后，系统究竟变好了还是变差了。

常用指标可以分成两部分：

- **检索是否找对：** Context Precision、Context Recall。
- **生成是否可靠：** Faithfulness、Response Relevancy（旧资料中也常写 Answer Relevancy）。
- **多模态场景：** 还可以关注 Multimodal Faithfulness 和 Multimodal Relevance。

指标不是越多越好，应根据是否有标准答案、是否包含图片，以及评测成本来选择。

**面试可以这样说**

> 引入 Ragas 是为了避免只靠人工感觉判断 RAG 效果，并且可以在修改切片策略、召回参数或提示词以后做回归对比。我会重点看 Context Precision 和 Context Recall，判断检索内容是否准确、是否遗漏；再看 Faithfulness 和 Response Relevancy，判断回答有没有得到上下文支持、有没有真正回答用户问题。如果是图文混合场景，还会补充多模态忠实度和相关性指标。

### 6. Faithfulness 和 Answer Relevancy 如何计算

**先理解**

两者关注的问题不同：

- **Faithfulness：回答有没有根据。** 先把回答拆成若干事实声明，再逐条判断是否能由检索上下文支持。

  `Faithfulness = 上下文能够支持的声明数 ÷ 回答中的声明总数`

- **Answer Relevancy：回答有没有答到点上。** 根据回答反向生成若干个可能的问题，再计算这些问题和原始问题向量的余弦相似度，最后取平均值。

  `Answer Relevancy = 多个反向生成问题与原问题的余弦相似度平均值`

高 Faithfulness 不代表回答一定正确。例如检索到的原文就是错的，回答完全照着原文说，忠实度仍可能很高。高 Answer Relevancy 也不代表事实正确，它只说明回答和问题比较相关。

**面试可以这样说**

> Faithfulness 会先把回答拆成多个声明，再逐条检查这些声明能否从检索上下文中推出，最后用“被支持的声明数除以总声明数”得到分数。Answer Relevancy 更关注是否答题，它会根据回答反向生成几个问题，再计算这些问题和原问题的向量相似度并取平均。一个衡量有没有依据，另一个衡量有没有答到点上，两者都不能单独代表最终答案完全正确。

## 三、项目深挖：LangGraph、记忆与安全护栏

### 7. LangGraph 相比 LangChain 有什么优势

**先理解**

LangChain 和 LangGraph 不是简单的替代关系：

- LangChain 更像一套大模型应用组件和高层 Agent 框架，模型、Prompt、Retriever、Tool 等接入比较方便，适合快速开始。
- LangGraph 更像一个有状态的工作流运行时。它把流程表示成节点和边，更方便实现循环、分支、状态保存、中断恢复和人工审批。

如果只是一个简单的“模型调用工具”循环，LangChain 往往已经够用；如果流程长、需要恢复、需要人工确认或需要精细控制状态，LangGraph 更合适。

**面试可以这样说**

> 我认为 LangGraph 的优势主要是可控性。它把 Agent 流程显式表示成节点、边和状态，所以复杂分支、循环、失败恢复、人工审批都更容易管理，而且支持 checkpoint 持久化。LangChain 的优势是抽象更高、组件集成多，做简单 Agent 上手更快。因此我不会说 LangGraph 一定比 LangChain 好，而是简单场景优先 LangChain，需要长流程和状态控制时再使用 LangGraph。

### 8. LangGraph 的状态快照机制如何实现

**先理解**

可以把 checkpoint 理解成游戏存档。Graph 每执行到一个步骤，就把当时的状态保存下来，例如消息、工具结果、下一步节点和相关元数据。

主要过程是：

1. 定义 Graph State，也就是流程中需要共享的数据。
2. 编译 Graph 时配置 checkpointer。
3. 每次执行使用 `thread_id` 区分不同会话。
4. 在执行步骤后，将状态序列化并写入内存、SQLite、PostgreSQL 等存储。
5. 失败或人工中断后，通过 `thread_id` 和 `checkpoint_id` 找到存档，从上一个成功状态继续执行。

**面试可以这样说**

> LangGraph 的快照机制本质上是给 Agent 工作流做存档。编译 Graph 时传入 checkpointer，运行时通过 thread_id 区分会话。每个执行步骤结束后，系统会保存当前状态、下一步节点和元数据，形成 StateSnapshot。出现异常或人工中断时，可以从最近的成功 checkpoint 恢复，而不用把整个流程重新跑一遍。开发环境可以用内存或 SQLite，生产环境通常使用持久化数据库。

### 9. 向量记忆库如何更新用户画像

**先理解**

不能把用户说的每句话都直接存成永久画像，否则会出现重复、矛盾和隐私问题。比较可靠的流程是：

1. 从对话中提取“可能值得长期记住”的信息，例如职业、稳定偏好和长期目标。
2. 判断是否涉及敏感信息，并让用户能够查看、修改或删除。
3. 以 `user_id` 建立命名空间，在旧记忆中做相似度检索。
4. 没有相似内容就新增；已经存在就更新；发生冲突时保留时间、来源和置信度，而不是直接覆盖。
5. 检索时按照相似度、时间和重要性综合排序，再生成当前用户画像。

向量库更适合“按语义找记忆”，而姓名、权限等需要强一致的数据，更适合放在结构化数据库中。

**面试可以这样说**

> 我的理解是先从对话里提取候选记忆，例如用户的长期目标和稳定偏好，然后在该用户的命名空间中检索相似记忆。没有相似记录就新增，有相似记录就做去重或更新；如果新旧信息冲突，还要保存时间、来源和置信度。向量库负责语义召回，结构化数据库负责保存需要强一致的画像字段。这样比把每句话都直接写入向量库更可靠。

### 10. 如何区分短期记忆和长期记忆

**先理解**

- **短期记忆：** 服务于当前会话，例如用户刚刚问了什么、工具刚返回什么结果。通常放在当前线程的 State 或 checkpoint 中。
- **长期记忆：** 跨会话保留，例如用户的职业方向、长期偏好和项目背景。通常按用户 ID 存入持久化 Store、数据库或向量库。

短期记忆不能无限增加，需要采用截断、摘要或选择性保留；长期记忆也不是永久保存所有内容，应有更新、过期和删除机制。

**面试可以这样说**

> 短期记忆主要解决当前会话的连续性，比如上一轮问题和刚执行完的工具结果，一般跟 thread_id 绑定并保存在 Graph State 中。长期记忆解决跨会话个性化，比如用户的长期目标和稳定偏好，一般按 user_id 持久化存储。短期记忆要控制上下文长度，长期记忆要做去重、更新、过期和隐私管理。

### 11. 安全护栏如何实现敏感内容拦截

**先理解**

只使用敏感词表很容易误杀，也很容易被同音字、拆字和编码绕过。比较完整的护栏应该是多层的：

1. **输入层：** 关键词和正则、PII 检测、内容分类器、Prompt Injection 检测。
2. **模型层：** 系统规则明确允许和禁止的范围；检索数据与用户指令分开处理。
3. **工具层：** 参数校验、最小权限、路径白名单、危险操作二次确认和超时限制。
4. **输出层：** 再次检测敏感内容，必要时脱敏、拒答或转人工。
5. **审计层：** 记录触发规则、模型版本和处理结果，持续分析误杀与漏检。

**面试可以这样说**

> 我不会只依赖敏感词表，而会做多层防护。输入先经过关键词、正则、PII 和分类模型检查；工具调用前再做参数校验、权限控制和高风险操作确认；模型输出后还要进行脱敏和内容复检。以我的 LeoClaw 为例，文件工具只能访问指定工作区，命令也有超时限制，这属于工具层护栏。最终还要记录日志，通过测试集持续评估误杀率和漏检率。

## 四、RAG 与向量检索

### 12. 在 RAG 中如何选择文档切片粒度

**先理解**

切片太小，会丢失上下文；切片太大，会混入无关信息、增加 Token 成本，并降低检索精度。因此不能只凭一个固定数字决定。

比较实用的步骤是：

1. 优先按标题、段落、表格和语义边界切分，不要从句子中间硬切。
2. 初次实验可从约 300～600 tokens、10%～20% overlap 开始，但这只是起点。
3. 表格、步骤说明和图注尽量保持完整，并保存章节、页码等元数据。
4. 长文档可以使用父子切片：小块负责检索，大块负责给模型补充上下文。
5. 用真实问题测试 Context Precision、Context Recall、正确率、延迟和 Token 成本，再调整大小与 overlap。

**面试可以这样说**

> 我会优先按文档结构和语义边界切片，而不是固定每 N 个字符切一次。粒度太小会丢上下文，太大会引入噪声。我通常会用一个中等大小作为起点，再根据真实问题评测召回率、精度和 Token 成本。工业文档中的表格、步骤和图注要尽量保持完整，必要时采用父子切片，让小块负责检索、大块负责补充上下文。

### 13. IVF_FLAT 和 HNSW 有什么区别，各自适用于什么场景

**先理解**

可以用“先分区再找”和“沿着导航图找”来区分：

| 对比项 | IVF_FLAT | HNSW |
| --- | --- | --- |
| 核心思路 | 先把向量聚类分区，查询时只搜索部分分区 | 把向量连接成多层近邻图，从高层向低层逐步导航 |
| 准确性 | 被选中分区内做精确距离计算，但可能漏掉其他分区中的结果 | 近似搜索，通常能取得较好的召回率和延迟平衡 |
| 构建 | 需要先训练聚类中心，构建相对直接 | 建图通常更慢 |
| 内存 | 通常比 HNSW 的图结构节省内存 | 需要保存额外邻接边，内存占用较高 |
| 调参 | `nlist` 控制分区数，`nprobe` 控制查询多少个分区 | `M`、`efConstruction`、`efSearch` 影响内存、构建、速度和召回率 |
| 适用场景 | 大规模、数据较稳定、内存受限或适合批量/GPU 搜索 | 内存充足、在线低延迟、高召回率、需要频繁查询或增量写入 |

**面试可以这样说**

> IVF_FLAT 是先聚类分桶，查询时只在最相关的几个桶中做精确距离计算，因此全局上仍然是近似搜索。它需要训练聚类中心，内存相对可控，适合大规模且相对稳定的数据。HNSW 是多层近邻图，通过图导航快速接近目标，通常低延迟和高召回表现更好，也方便增量插入，但建图慢、占用内存更多。实际选择要用自己的数据比较召回率、P95 延迟、构建时间和内存，而不是只看理论。

## 五、大模型原理与应用工程

### 14. 什么是 CoT，为什么它能提高复杂任务能力

**先理解**

CoT 是 Chain of Thought，即让模型在得出答案前，把复杂问题拆成若干中间步骤。它对数学题、逻辑题、规划题和多步决策更有帮助，因为模型不用从问题直接“跳”到最终答案，而是逐步缩小问题。

但 CoT 不是正确性的保证：推理过程本身也可能出错，而且会增加 Token 和延迟。工程中最好再配合计算器、代码执行、检索和结果校验。

**面试可以这样说**

> CoT 就是让模型把复杂问题拆成中间步骤再得出答案。它相当于给模型增加了一个可展开的计算过程，能够减少一步跳到结论造成的错误，所以在数学、逻辑和规划任务中通常更有效。但它只是提高成功概率，不代表推理一定正确。生产系统中还需要结合工具调用、结果验证和评测，不能只相信模型生成的推理文字。

### 15. 大模型应用中常见的幻觉有哪些，工程上如何缓解

**先理解**

常见幻觉包括：

- **事实幻觉：** 编造不存在的人、数据或事件。
- **上下文幻觉：** 回答和给定文档矛盾，或者把文档没说的内容当成事实。
- **引用幻觉：** 编造论文、网址、页码或引用内容。
- **工具幻觉：** 调用不存在的工具、生成错误参数，或者声称工具已经成功执行。
- **逻辑和计算幻觉：** 推理看起来流畅，但步骤或数字错误。

缓解方式：

1. 用可信数据做 RAG，并同时评估检索质量，避免“检索错了，模型只能跟着错”。
2. 要求答案附带来源；对数字、日期和关键事实再次验证。
3. 使用结构化输出和参数 Schema，工具执行前做类型、权限与业务规则校验。
4. 给模型设置“证据不足时拒答”的规则，并为低置信度结果设置人工复核。
5. 建立固定评测集、线上监控和错误案例库。降低 temperature 只能减少随机性，不能根治幻觉。

**面试可以这样说**

> 我会把幻觉分成事实幻觉、上下文幻觉、引用幻觉、工具调用幻觉以及逻辑计算错误。工程上不能只靠 Prompt，而要从数据、模型和执行三个层面处理：先用可信知识库提高检索质量，再要求关键结论可追溯；工具参数要经过 Schema 和权限校验；证据不足时允许模型拒答。最后通过固定评测集和线上日志持续收集失败案例。降低 temperature 有帮助，但不能从根本上解决幻觉。

### 16. Function Call 的完整流程是什么，模型如何知道调用哪个工具

**先理解**

模型本身通常不会直接执行 Python 函数。它负责“提出调用请求”，真正执行工具的是应用程序。

完整流程是：

1. 开发者把工具的名称、用途说明和参数 JSON Schema 一起发给模型。
2. 模型根据用户问题、系统指令和工具描述，决定直接回答还是生成工具调用。
3. 模型返回工具名和结构化参数，例如 `read_file({"file_path": "README.md"})`。
4. 应用程序校验参数、权限和风险，再执行真实函数。
5. 应用程序把工具结果和对应的 `tool_call_id` 交回模型。
6. 模型根据工具结果继续调用其他工具，或者生成最终答案。

模型之所以知道选哪个工具，主要依靠训练中学到的工具调用能力，以及运行时提供的工具名称、描述、参数 Schema、示例和系统规则。工具描述写得含糊，模型就更容易选错。

**面试可以这样说**

> Function Call 可以分成“模型决策”和“程序执行”两部分。应用先把工具名称、描述和参数 Schema 提供给模型，模型根据用户意图选择工具并返回结构化参数。程序收到后不能马上盲目执行，而要先校验参数、路径和权限，再调用真实函数，并把结果回传给模型，最后由模型组织答案。我的 LeoClaw 就是类似流程：模型可以选择文件读取、写入、检索或命令工具，但真正执行的是 Python 程序，而且工具只能在指定工作区内操作。

## 六、推理部署

### 17. vLLM 中 PagedAttention 的原理

**先理解**

大模型逐字生成时，需要保存以前 Token 的 Key 和 Value，也就是 KV Cache。不同请求长度不一样，如果每个请求都提前申请一整块连续显存，会出现大量浪费和碎片。

PagedAttention 借用了操作系统“分页”的思想：

1. 把每个请求的 KV Cache 切成固定大小的逻辑块。
2. 逻辑块可以映射到不连续的物理显存块，不要求整段 KV Cache 连续存放。
3. 请求生成新 Token 时按需分配新块，结束后及时回收。
4. 相同前缀还可以共享物理块，需要修改时再复制。

它主要优化显存管理，使服务器能同时容纳更多请求并提高吞吐量，并不是一种让模型回答更聪明的新 Attention 公式。

**面试可以这样说**

> PagedAttention 主要解决 KV Cache 的显存浪费问题。传统方式容易为不同长度的请求预留连续显存，造成内部浪费和外部碎片。vLLM 把 KV Cache 切成固定大小的块，通过块表把逻辑块映射到不连续的物理显存块，按需分配和回收，思路类似操作系统虚拟内存分页。这样能提高显存利用率，支持更大的连续批处理，从而提升推理吞吐量。

## 七、Python 与 Web 基础

### 18. Python 中列表和元组有什么区别

**先理解**

| 对比项 | 列表 `list` | 元组 `tuple` |
| --- | --- | --- |
| 写法 | `[1, 2, 3]` | `(1, 2, 3)` |
| 是否可变 | 可以增删改 | 创建后不能修改元素位置和引用 |
| 常见用途 | 会变化的数据集合 | 固定结构的数据、函数返回多个值 |
| 能否作为字典键 | 不可以 | 当所有元素都可哈希时可以 |

“元组不可变”不代表元组内部的可变对象也会被冻结。例如 `([1, 2], 3)` 中的列表仍然可以修改。

**面试可以这样说**

> 列表是可变序列，可以增加、删除和修改元素；元组是不可变序列，创建以后不能替换其中的元素。需要动态维护的数据通常用列表，表示固定结构或不希望被修改的数据可以用元组。元组中的元素如果都可哈希，还可以作为字典键。性能差异通常不是我选择它们的第一原因，语义和是否需要修改更重要。

### 19. Python 装饰器是什么，有哪些应用场景

**先理解**

装饰器是在不修改原函数主体的情况下，为函数增加一层通用逻辑。`@decorator` 本质上相当于 `func = decorator(func)`。

```python
from functools import wraps
from time import perf_counter


def timer(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        start = perf_counter()
        result = func(*args, **kwargs)
        print(f"耗时：{perf_counter() - start:.3f}s")
        return result

    return wrapper


@timer
def add(a, b):
    return a + b
```

常见场景有日志、计时、权限校验、缓存、重试、事务和 Web 路由。`functools.wraps` 用来保留原函数的名称和文档等元数据。

**面试可以这样说**

> 装饰器本质上是一个接收函数并返回新函数的可调用对象，`@` 只是语法糖。它可以在不修改业务函数代码的情况下，统一增加日志、计时、权限、缓存或重试逻辑。实现时通常在内部定义 wrapper，并使用 `*args` 和 `**kwargs` 转发参数，同时用 `functools.wraps` 保留原函数信息。

### 20. HTTP 中 GET 和 POST 请求有什么区别

**先理解**

| 对比项 | GET | POST |
| --- | --- | --- |
| 主要语义 | 获取目标资源的当前表示 | 把数据提交给目标资源处理 |
| 安全方法 | 是，按规范不应改变服务端状态 | 不是，可能创建或修改状态 |
| 幂等性 | 是，多次相同请求预期效果相同 | 通常不是，多次提交可能产生多条数据 |
| 参数位置 | 常见于 URL 查询参数 | 常见于请求体，但并不是协议层唯一限制 |
| 缓存 | 浏览器和中间缓存通常更容易缓存 | 规范允许特定情况下缓存，但实践中较少 |

GET 参数出现在 URL 中，更容易进入历史记录和日志，但 POST 也不是自动加密的。真正保护传输内容依靠 HTTPS，敏感信息还要配合鉴权和日志脱敏。

**面试可以这样说**

> GET 的语义是获取资源，它属于安全、幂等方法，所以相同 GET 重复执行通常不应改变服务端状态。POST 是提交数据给服务端处理，常用于创建资源或执行操作，通常不保证幂等。GET 参数常放在 URL，POST 数据常放在请求体，但两者是否安全都取决于 HTTPS、鉴权和服务端实现，不能简单说 POST 天生更安全。

## 八、算法题

### 21. 手撕：无重复字符的最长子串

**先理解**

使用滑动窗口。右指针不断向右移动，字典记录每个字符最近一次出现的位置。如果当前字符已经在窗口中出现，就把左边界移动到该字符上次位置的下一位。

```python
def length_of_longest_substring(s: str) -> int:
    last_index = {}
    left = 0
    answer = 0

    for right, char in enumerate(s):
        # char 在当前窗口中重复，移动左边界
        if char in last_index and last_index[char] >= left:
            left = last_index[char] + 1

        last_index[char] = right
        answer = max(answer, right - left + 1)

    return answer
```

以 `abcabcbb` 为例：窗口先扩大为 `abc`；再次遇到 `a` 时，把左边界移动到第一个 `a` 后面。整个过程中左右指针都只向前移动。

- 时间复杂度：`O(n)`。
- 空间复杂度：`O(min(n, 字符集大小))`。

**面试可以这样说**

> 我使用滑动窗口和哈希表。哈希表保存字符最后出现的位置，右指针负责扩展窗口；遇到窗口内的重复字符时，把左指针移动到上次出现位置的下一位。每个字符最多被左右指针处理一次，所以时间复杂度是 O(n)，空间复杂度是 O(min(n, 字符集大小))。
